# Доступ рабочих станций

Рабочая станция авторизуется по IP. У неё нет личного кабинета, пароля пользователя сайта и операции выхода из IP-авторизации. Интерфейс не показывает меню ни для `principal_type=workstation`, ни для устаревшего представления с `role=workstation`. Если учётная запись пользователя авторизована корректным JWT на том же компьютере, она остаётся отдельным пользовательским субъектом со своими правами.

Auth-service всегда возвращает для IP-субъекта роль `workstation` и только разрешения чтения назначенных аудиторий и управления WAN в них, независимо от ошибочного `role_id` в БД. Создание/изменение рабочей станции через внутренние схемы допускает только роль `workstation`.

Gateway дополнительно ограничивает разрешения рабочих станций и проверяет пользовательский тип субъекта для административных действий: обслуживания, неактивных/служебных аудиторий, привилегированных действий Veyon, Ctrl+Alt+Del и команд с получением вывода. Обновление учётной записи через `PATCH /api/me` запрещено. Все административные маршруты отклоняют запрос до обращения к внутренним сервисам. Доступ к аудиториям и устройствам остаётся ограничен назначениями. Чтение `/api/me` и `/api/classrooms` нужно для загрузки приложения и остаётся доступным в этих пределах. Отдельного API выхода нет: выход пользовательской учётной записи очищает JWT в браузере.

Обычные действия Veyon в назначенной аудитории, включая вход/выход пользователя удалённой Windows, сохраняются. Они не являются изменением учётной записи сайта. Одноразовые callback/script-маршруты команд требуют собственного секретного токена задания; IP-авторизация станции не заменяет такой токен.

## IP и WireGuard

Встроенный nginx перезаписывает `X-Forwarded-For` значением `$remote_addr`, не добавляя присланную клиентом цепочку. При обычном запросе браузера результат совпадает с прежним значением, но подстановка произвольного IP заголовком исключена. Публичный порт gateway привязан к loopback сервера, остальные внутренние API доступны в Docker-сети.

Обычная маршрутизация через WireGuard сохраняет внутренний исходный IP. При NAT/masquerade nginx видит адрес после трансляции; заголовок не может восстановить потерянный исходный адрес. Если перед приложением установлен отдельный HTTP reverse proxy, сначала нужно настроить в nginx доверие к IP только этого прокси и восстановление реального адреса (`set_real_ip_from`, `real_ip_header`), затем перезаписывать заголовок. Произвольным клиентским заголовкам доверять нельзя.

## Проверки и установка

Параметризованные проверки перебирают все `/api/admin/*` из реального реестра маршрутов, а также личный кабинет и административные действия Veyon. Проверяются нормальная станция и станция с ошибочной ролью admin/superadmin и всеми разрешениями. Отдельно проверены канонизация IP-субъекта и границы назначенных аудиторий. В браузере проверено отсутствие меню на ПК/мобильных экранах и сохранение разрешённых действий.

```bash
bash scripts/compose-up.sh cmnc-auth-service cmnc-api-gateway cmnc-web
```

Миграции и изменения `.env` не требуются. На Ubuntu выполнена только проверка конфигурации nginx и клиентских IP в журналах; установка изменений на сервер не выполнялась.
