# Камеры: зависания, фоновые процессы и RTSP СитиМолл

Проверено 10 ноября 2026 года через предоставленный SSH-доступ. Рабочие
контейнеры не изменялись и не перезапускались. Изменения подготовлены в проекте.

## Найденные дефекты и исправления

1. `CameraSessionStore.get()` удалял истёкшую сессию раньше фоновой очистки.
   После этого очистка не могла удалить её ID из списка зрителей FFmpeg.
   Исправлено: истёкшие записи остаются до освобождения потока; get только
   возвращает отсутствие сессии. При получении HLS продлевается срок активности.
2. Потерянный DELETE при закрытии браузера оставлял сессию на час. Добавлен
   предел отсутствия запросов 90 секунд, проверка каждые максимум 10 секунд,
   закрытие с keepalive при pagehide. Затем действует прежняя пауза остановки
   общего потока 45 секунд, если других зрителей нет. Активный просмотр
   продлевает сессию, а не обрывается через фиксированный час.
3. Живой процесс FFmpeg мог не обновлять HLS. Теперь отсутствие обновления
   плейлиста около 30–35 секунд приводит к завершению и восстановлению worker.
   Слишком старый плейлист возвращает 503 вместо выдачи старого ролика.
4. Перезапуск использует отдельный префикс имён сегментов. Старые URL не
   начинают ссылаться на новые байты. История последовательности и
   discontinuity сохраняется через append_list; незадействованные сегменты
   удаляются регулярно с запасом на загрузку предыдущего плейлиста.
5. В старых логах много `Non-monotonic DTS`/`Queue input is backward in time`.
   Убрана принудительная подстановка системных часов вместо RTSP timestamps.
   Видео нормализуется с ограничением скачка между кадрами двумя секундами,
   аудио получает монотонные метки по числу сэмплов. Это не даёт fps-фильтру
   создавать час дубликатов при скачке часов и убирает обратный ход аудио.
6. Параллелизм декодирования/кодирования ограничен настройкой, по умолчанию
   два потока. На несколько реально открытых камер нагрузка закономерно выше.
7. Плеер пересоздаёт утратившую активность сессию через 30 секунд отсутствия
   продвижения воспроизведения. Это восстанавливает не только MediaSource,
   но и истёкший server session ID. Возврат страницы из BFCache открывает сессию
   заново. Истёкшие сессии не могут удерживать FFmpeg бесконечно.

## СитиМолл: отдельная причина разрывов

Прямой RTSP даёт H.264 640×360, 25 FPS, без звука. Соединение сбрасывается
удалённой стороной через 2–5 секунд: FFmpeg фиксирует `Connection reset by peer`,
затем EOF; процесс при этом может завершиться с кодом 0.

Результат воспроизведён без нашего API и HLS, в том числе без перекодирования.
Проверены основной и дополнительный потоки, другой User-Agent и альтернативный
RTSP-путь. UDP не получил видеоданные и завершился по timeout. Поэтому
исправления HLS помогают переносить переподключения, но не устраняют сброс
соединения камерой, NVR или устройством на сетевом пути. Для полного устранения
нужна отдельная проверка этого пути и логов источника. Рабочий URL и настройки
самой камеры не менялись. RTSP-реквизиты в отчёт не включены.

## Настройки

```dotenv
CMNC_CAMERA_VIEWER_IDLE_TIMEOUT_SECONDS=90
CMNC_CAMERA_STREAM_STALL_TIMEOUT_SECONDS=30
CMNC_CAMERA_FFMPEG_THREADS=2
```

Compose теперь передаёт также ранее перечисленные в .env.example режим видео,
аудио, FPS, CRF, размер, preset/profile/level и задержку остановки. Пустой
VIDEO_MODE сохраняет прежнюю семантику TRANSCODE_VIDEO. Индивидуальное качество
основного/дополнительного потока камеры сохраняется.

## Проверка и применение

15 тестов прошли локально и в отдельном временном контейнере на сервере на
базе текущего рабочего образа. Нативный FFmpeg-тест проверяет скачок времени
на час, монотонность аудио, четыре смены worker и разные URL сегментов.
Тесты не подключаются к реальным камерам. Браузерная проверка на ПК и мобильной
ширине подтверждает замену зависшей сессии и освобождение предыдущей. WEB собирается; в линтере плеера
остаётся прежнее замечание set-state-in-effect для выбора качества.

```bash
bash scripts/compose-up.sh cmnc-camera-service cmnc-web
```

RabbitMQ рассматривается отдельно: камера не передаёт через него медиаданные.
Причина его пиков CPU и оценка отказа от брокера — в rabbitmq-assessment.md.
