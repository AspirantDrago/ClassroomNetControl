# Порядок запуска контейнеров

Compose запускает независимые ветви параллельно. Порядок записей в YAML не задаёт очередь.
`service_healthy` означает ожидание первой успешной проверки готовности.

| Сервис | Чью готовность ждёт | Причина |
| --- | --- | --- |
| PostgreSQL, RabbitMQ | Никого | Базовые сервисы запускаются параллельно |
| Auth | PostgreSQL | Миграции и создание первого суперадминистратора |
| Classroom | PostgreSQL, RabbitMQ | Миграции, подключение к очередям политик и статистики |
| Inventory | PostgreSQL, RabbitMQ | Миграции и подписка на DHCP-события |
| API gateway | Auth, Classroom, Inventory | Вход, проверка доступа и загрузка аудитории |
| Web | API gateway | Интерфейс открывается после готовности основного API |
| MikroTik poller | RabbitMQ, Inventory | Список маршрутизаторов и публикация DHCP-событий |
| Policy sync | RabbitMQ, Classroom, Inventory | Очередь политик, правила и настройки маршрутизаторов |
| Camera, Maintenance | Никого | Подключаются по запросам, не блокируют API/Web |

Критическая цепочка для интерфейса:

```text
PostgreSQL ──┬── Auth ──────────────────┐
             ├── Classroom ─────────────┼── API gateway ── Web
             └── Inventory ─────────────┘
RabbitMQ ──────── Classroom + Inventory
```

Poller и Policy sync запускаются отдельными ветвями и не входят в эту цепочку.
Без Poller интерфейс может показывать сохранённые данные, но новые DHCP-состояния
не поступают. Без Policy sync изменения WAN не применяются на MikroTik, пока
синхронизация не восстановится. Camera и Maintenance нужны только своим функциям.

## Оптимизация проверок готовности

- Python-сервисы: при старте каждые 2 секунды, после готовности — каждые 30 секунд.
- PostgreSQL: при старте каждые 2 секунды, после готовности — каждые 10 секунд.
  Проверяется TCP на `127.0.0.1`, чтобы временный сервер инициализации,
  доступный только через Unix-сокет, не объявлял контейнер готовым раньше создания БД.
- RabbitMQ: при старте каждые 5 секунд, после готовности — каждые 10 секунд.
  Проверяются работа приложения и доступность TCP-слушателей; одного `ping` недостаточно.
- Ошибки проверок игнорируются первые 60 секунд для Python и 120 секунд для инфраструктуры.
  Это не фиксированная задержка: первая успешная проверка сразу освобождает зависимые сервисы.
- Проверки не зависят от доступности самих маршрутизаторов MikroTik.
- Web использует сеть хоста; дублирующее сопоставление `ports` удалено.

`start_interval` требует Docker Engine 25+ и Docker Compose 2.20.2+.

## Запуск

Все сервисы (без принудительного пересоздания неизменившихся контейнеров):

```bash
bash scripts/compose-up.sh
```

Минимальный набор для входа и отображения сохранённых данных:

```bash
docker compose -f infra/docker-compose.yml --env-file .env up -d --build cmnc-web
```

Эта команда автоматически поднимает зависимости Web. Рабочий `scripts/compose-up.sh`
с явно указанными сервисами использует `--no-deps --force-recreate`, поэтому он
принудительно перезапускает только выбранные сервисы; нужные зависимости уже должны
быть запущены. Обычный `up` допускает параллельный
старт независимых ветвей; разносить полный запуск на последовательные команды не нужно.

При изменении только параметров Compose пересборка образов не требуется:

```bash
docker compose -f infra/docker-compose.yml --env-file .env up -d --no-build
```

Compose пересоздаст контейнеры с изменившейся конфигурацией. Запуск без `--force-recreate`
не требует пересоздания контейнеров с неизменившейся конфигурацией.

## Проверка конфигурации

```bash
docker compose -f infra/docker-compose.yml --env-file .env config --quiet
```
